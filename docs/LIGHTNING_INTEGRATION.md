# Lightning integration

CircleSats supports two server-side **receivers** behind the same invoice/status methods. LNbits uses `POST /api/v1/payments` with `out:false` and `GET /api/v1/payments/{checking_id}`. NWC uses the official Alby JavaScript SDK's `getInfo`, `makeInvoice`, and `lookupInvoice`; invoice amounts are converted from sats to millisats. The NWC receiver rejects a missing permission or a network that differs from `LNBITS_NETWORK`. `LNBITS_NETWORK` is retained as the common expected network setting for both providers.

The server stores member, group, cycle, round, amount, checking ID, payment hash, invoice text, provider, environment, and timestamps together. A `paid` flag alone is insufficient. The LNbits adapter requires the checking ID, exact expected amount in the unit returned by the provider, matching hash and invoice, and acceptable status. NWC checks incoming direction, settled state, hash, invoice, and amount. For a genuine Signet configuration, CircleSats also decodes the BOLT11 invoice before storage and rejects a wrong network, amount, hash, or expiry. The store prevents duplicate active contributions and reused payment hashes; its serialized mutation queue avoids double credit within one process. Failed or unreachable lookups leave the last verified state intact. Startup refuses to reuse a ledger with simulated records or Lightning records from a different or unknown environment.

The **payer** connection is a different NWC secret entered by the signed-in member into the browser. It stays in memory, is cleared on sign-out, and is rejected for in-app payment if its network differs from the receiver. The member explicitly clicks to pay. An externally paid invoice can be observed by the receiver, but payer attribution remains unverified. When a connected payer returns a preimage, the server checks SHA-256(preimage) against the recorded payment hash before labelling it `member-proof`.

The deterministic unit tests remain separate from the live integration check. On 26 October 2026, `npm run test:sandbox` connected two Alby Developer Sandbox wallets and passed four 100 sat **fake-sat** payments through CircleSats' HTTP app. Each settled incoming invoice matched its stored invoice, hash, and amount; the payer returned a matching preimage; duplicate member invoices were rejected; the 400 sat funded round gained three nonrecipient approvals; reloaded JSON retained the receipts and approved state. The sanitized record is in ignored `data/alby-sandbox-evidence.json`. The same payer wallet paid all four invoices, so this verifies account proof handling, not four independent payer identities. No outgoing payout was made. No signet, LNbits, or real Bitcoin payment has been verified.

Alby's sandbox reports `mainnet` over NWC despite using fake sats. CircleSats identifies it as `alby-sandbox`, labels it as test sats, and binds browser payment to a configured sandbox payer public key as well as the reported network. The sandbox faucet's receiver URL currently includes `pay_invoice`; the normal receiver rejects that permission. `ALLOW_SANDBOX_RECEIVER_SPEND_PERMISSION=1` works only with `PAYMENT_ENVIRONMENT=alby-sandbox` and should never be used for a real wallet. Relay timeouts were intermittent during verification; retries may be needed when starting the sandbox. The local runtime enables normal certificate validation and uses Node's system CA store rather than disabling TLS checks.

The [Bitcoin Connect](https://github.com/getAlby/bitcoin-connect) wallet modal was evaluated but not added. It is currently marked alpha and saves wallet connections to localStorage by default. The existing payer UI keeps its NWC secret in tab memory, checks sandbox wallet identity, and retains invoice copy and QR choices. The [Alby Bitcoin Builder Skill](https://github.com/getAlby/builder-skill) was reviewed as an agent reference, with no runtime dependency needed.
