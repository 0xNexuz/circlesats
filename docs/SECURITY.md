# Security and trust boundaries

| Risk | Current control | Remaining limit |
| --- | --- | --- |
| Forged contribution | Server asks the configured receiver for incoming settled status, exact amount, hash, and invoice; client cannot set `paid` | Four fake-sat sandbox settlements passed; signet, LNbits, and real Bitcoin remain unverified |
| Replay or double credit | Case-insensitive unique 64-hex payment hashes, one active member contribution per round, serialized writes; expired invoices continue provider reconciliation until a definitive result | One locked production Node process only; an uncertain invoice cannot be replaced until the provider declares it failed or expired |
| Unauthorized member action | Access-code sessions, HttpOnly SameSite cookie, CSRF token, server-side role checks; production requires a loopback proxy IP header for per-client sign-in limits, and guest sessions have a per-IP cap | Access codes can be shared; no legal identity verification; proxy must overwrite `X-Real-IP` and add network-level rate limits |
| Payout fraud | All nonrecipient members approve; recipient cannot approve; organizer reference stays unverified | A real transfer cannot currently be independently verified or completed |
| Wallet-secret leak | Receiver credentials in ignored environment files or host secret store; production member codes provisioned privately, not printed by server; real-wallet NWC receiver rejects `pay_invoice`; payer URI stays in browser tab memory | Alby Sandbox faucet grants its fake-sat receiver spending permission; this exception requires explicit sandbox-only opt-in. Browser device compromise and treasurer custody remain external risks |
| Invoice substitution | Server stores original invoice/hash and compares status response before credit | Users should confirm wallet network and recipient in their wallet |
| Cross-group access | Guest demo uses private in-memory store; shared members are restricted to seeded group | Multi-group production membership is not implemented |
| Real practice payments (Vercel `/api/practice`) | The functions hold only the treasurer node's receive-only NWC connection (spending permission rejected). They ask the Mutinynet faucet to pay an invoice only after the treasurer node confirms it issued it, for exactly 100 sats, still pending and unexpired; a settled invoice is never paid twice. Credit needs treasurer settlement and a preimage hashing to the payment hash, rechecked in the browser. The faucet callback must be on the faucet's own origin. Best-effort limit of 30 requests per 10 minutes per address and instance | Depends on the public Mutinynet faucet and on the treasurer node being online with incoming capacity. Invoice spam can still create unpaid invoices on the treasurer node. Test coins only; receipts prove a Mutinynet Lightning payment by the faucet, not who the judge is |
| Real-sat practice invoices (Blink, mainnet) | The server holds only a Blink API key with Read + Receive; a key with Write is refused at startup, and the network must be mainnet. CircleSats creates 100-sat invoices and checks them by payment hash on the treasurer's own wallet (exact invoice and amount); it never pays mainnet invoices. Preimages returned by Blink are checked against the hash in the server and again in the browser | Visitors send real sats to the demo treasurer and are told they are not refunded. Blink is custodial and its account limits apply. A missing preimage is shown as unavailable rather than invented |
| Guest sandbox wallets | Each guest demo gets its own newly created Alby sandbox receiver and payer (test sats). Their NWC secrets stay in that session's memory (server) or tab (Vercel), never in the ledger, responses, or logs. A guest payment is credited only after the guest's receiver reports it settled with matching invoice, hash, amount and preimage. At most 50 open on a host; closed on logout or session expiry | Relies on the public `faucet.nwc.dev` service; abuse protection is the existing guest-session cap per address. Sandbox receipts are labelled test sats and are not evidence of signet or real Bitcoin settlement |
| Network confusion | Payer network must match receiver; Alby Sandbox is labelled fake sats and its payer public key must match the configured sandbox wallet | The sandbox NWC API reports `mainnet` for fake sats, so operators must never mix sandbox and real wallet credentials |
| Ledger corruption or duplicate server | Flushed version-4 JSON, SHA-256 checksum, prior validated backup, production instance lock, and fail-closed load | Run on one local persistent volume; make off-host backups and rehearse manual restore |
| Browser and transport abuse | HTTPS-required production configuration, Secure/HttpOnly/SameSite cookies, CSRF checks, CSP, frame denial, no-sniff, HSTS, and sanitized error logging | Reverse proxy and host firewall must actually enforce HTTPS and restrict the Node listener |

Only the treasurer wallet actually controls funds. The app does not hold escrow, guarantee payouts, or know the wallet's current spendable balance and fees. Demo sats and simulated settlements are visibly separate from Lightning payments. Avoid using mainnet funds in this prototype. Never commit `.env`, access codes, wallet backups, or `data/`.

The desktop shell was observed with `NODE_TLS_REJECT_UNAUTHORIZED=0`. `scripts/start.js` removes that inherited override before the server imports networking code; direct server startup rejects the override even without a receiver. Sandbox commands use Node's system CA store. A certificate failure must be fixed with a trusted CA, never by disabling validation. The simulated demo does not contact a receiver.

The four-sandbox-payment test used **one** payer wallet for all member invoices. A signed-in account presenting a matching preimage is recorded as `member-proof`; this verifies control of that payment proof, not the legal identity of the human payer. The receiver credential and payer wallet URLs are in ignored local files, and the sanitized evidence contains hashes and amounts only. On 27 October 2026, `npm run check:secrets` scanned 53 Git candidate files against both private sandbox wallet connections and passed; `npm audit --omit=dev --audit-level=moderate` reported zero vulnerabilities. No signet, LNbits, or real payout settlement was independently verified.
