## Judge Lightning sandbox — 27 October 2026 (branch `claude/judge-lightning-sandbox`)

- Goal from the user: the easiest in-app Lightning transaction that anyone, including judges, can test without disrupting others; UI design unchanged.
- Each guest demo's existing **Create demo wallet → Get demo sats → Create demo contribution → Pay with demo wallet** buttons now use a private pair of Alby Developer Sandbox wallets created from `faucet.nwc.dev` for that visitor: a real BOLT11 invoice from the receiver, paid over NWC by the payer, credited only after receiver lookup shows it settled with matching invoice, hash, amount, and SHA-256(preimage). On the Vercel preview this runs in the visitor's tab; on the Node app it runs server-side per guest session (`GUEST_LIGHTNING_SANDBOX=0` disables it). Unreachable or slow (25 s) sandbox → the original simulation, unchanged.
- Code: `src/sandbox-lightning.js` (faucet + NWC pair, browser-compatible), `src/guest-sandbox.js` (guest wallet/invoice/pay actions), wiring in `src/app.js`, `src/browser-demo.js`, `src/auth.js` (closes wallets when a session ends), `src/server.js`; `store.syncWallet`; Vercel CSP `connect-src` adds `https://faucet.nwc.dev wss:`. UI changes are text only, where "simulated / not a Lightning transaction" would otherwise be false for a sandbox wallet.
- Verification in a cloud session without npm registry access: dependencies rebuilt from upstream sources at the locked versions; Node 22 (project pins 24). Baseline 25/25 passed before changes; 33/33 after (8 new). Chromium drove the built Vercel preview with the production CSP and a stand-in faucet/NWC hub: two isolated judges each paid one invoice (100 test sats each, separate wallets), offline fallback stayed simulated. The Node app started with the default and fell back cleanly with no internet. **Not yet run: `npm run test:guest-sandbox` against the live faucet; a live browser run on Vercel.**

## Evidence limits

No live CircleSats LNbits, Mutinynet/signet, or real-Bitcoin payment has been verified. Alby Sandbox uses fake sats and reports `mainnet` through NWC; its invoice settlement is not signet or real mainnet evidence. Its faucet receiving URL grants `pay_invoice`, so CircleSats rejects that for normal receivers and allows it only with `PAYMENT_ENVIRONMENT=alby-sandbox` plus an explicit opt-in. Sandbox wallet URLs and local UI config live only in ignored files. Relay connections were intermittent. No Docker/LNbits setup, deployment, public repo, demo video, or submission was completed. Real payout claims remain unverified and cannot advance a Lightning-mode round.

The full completion flow is **simulated only**. Simulated sats are explicitly labelled and kept in a private guest store or demo ledger, never mixed with real provider records. An access code and preimage can bind a payment to an account but do not establish legal identity. The treasurer's external wallet retains custody; CircleSats has no escrow.

## Decisions to preserve

- Keep the forest-green/gold visual identity and preloader. The user requested the preloader on every full reload; preserve that behavior with real asset readiness, fallback, and reduced motion.
- Keep a clear no-setup visitor demo. Never require judges to install or fund a wallet to see a full savings rotation.
- Use receive-only server credentials for real wallets. The Alby faucet's fake-sat receiver needs a sandbox-only spending-permission exception. The payer's bounded NWC connection remains in browser memory and requires an explicit pay action. Sandbox browser payer is additionally bound to the configured public wallet key.
- Treat LNbits/NWC stand-in tests as local tests only. The separate Alby Sandbox payments are actual fake-sat service interactions, not real Bitcoin settlement. Keep proof and settlement labels honest.
- Do not push, publish, deploy, submit, or add real spending permissions without the user's authorization.
